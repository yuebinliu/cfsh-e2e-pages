认识 CF Static Export Pro：一套插件，两种建站方式

Posted on October 19, 2026 by admin

一句话简介

CF Static Export Pro 把「文章单页」预渲染成静态 HTML 放进 Cloudflare R2，把「列表页」交给 D1 实时查询。 既能把现有 WordPress 站搬上 Cloudflare，也能不装 WordPress，直接用内置 CMS 建站。

它不是一个”整站生成器”，也不是一个纯动态博客。它刻意把页面分成两类：

页面 形态 存在哪 更新方式
文章单页 静态 HTML R2 发布 / 重建时写入
首页、分类、标签、归档、搜索 动态渲染 D1 + Worker 请求时实时查询
CSS / JS / 字体 静态资源 Worker assets 随部署上传，边缘免费直出

这样做的直接好处是：单页访问不碰数据库，列表页永远是最新的。

它解决什么问题

传统的 WordPress 静态化插件通常有两个极端：

  • 全站静态：快，但首页、分类页不会自己更新，每次发文都要重新生成整站；
  • 纯动态：实时，但每个请求都要跑 PHP + 查数据库，流量一上来就顶不住。

这套方案的取舍是：只把最重、最不需要变化的部分静态化。一篇文章发布后正文基本不变，适合预渲染；列表页每次发文都变，适合实时查。

两种用法

1. WordPress 插件

保留 WordPress 的编辑、媒体库、插件生态。插件负责：

  • 把文章同步进 D1（结构化字段：标题、slug、分类、标签、摘要、评论状态）；
  • 生成静态单页并上传 R2；
  • 把现有主题”抓”成风格包（tpl.json + CSS/JS/图片），供 Worker 渲染列表页使用；
  • 支持 S3 / R2 / GitHub / Netlify / Vercel / FTP / WebDAV / 本地目录等多种出口。

2. 独立 Worker CMS

不依赖 WordPress。部署一个 Worker，绑定 D1、R2、KV，打开 /admin/ 初始化管理员，就能：

  • 用 Markdown 或富文本写文章；
  • 管理分类、标签、媒体库；
  • 在线切换风格、编辑模板；
  • 管理媒体库、审核评论；
  • 批量发布、重建、导出。

两条路线共用同一套数据结构和渲染器，所以你可以先从 WordPress 开始，之后再慢慢把写作入口搬到 CMS。

适合谁

  • 已经有 WordPress 站，想上 Cloudflare 但又不想放弃现有内容；
  • 想要一个几乎零运维的博客 / 文档站，能接受 Cloudflare 的技术栈；
  • 喜欢折腾静态站，但不想每次发文都跑一遍 CI 构建。

接下来读什么

  • 想先看效果：本站就是用它跑的，你可以直接翻使用指南；
  • 想动手：从5 分钟搭起一个独立 CMS开始；
  • 想知道内部怎么运转：动静分离是怎么工作的。

动静分离是怎么工作的：D1、R2、KV 各管什么

Posted on October 18, 2026 by admin

一次访问发生了什么

以访问一篇文章 https://example.com/hello/ 为例：

  1. 请求先经过 Cloudflare 边缘的 assets 层。CSS、JS、字体、主题图片命中就直接返回，不计 Worker 调用；
  2. 没命中静态资源，进入 Worker；
  3. Worker 按路径算出 R2 key（默认 hello/index.html），读 R2；
  4. 命中 → 直接返回 HTML。评论区有标记时，额外查一次 D1 把最新评论注入；
  5. 未命中 → 从 D1 按 slug 取文章，用当前风格模板现场渲染，回填 R2 后返回。

访问首页 / 则是另一条路径：不走 R2，直接查 D1 取最近 N 篇，套 pageHome 模板渲染。列表结果会进边缘缓存（Cache API），按 TTL 过期。

三层存储的分工

层 存什么 为什么
R2 文章单页 HTML、媒体文件、风格包资源 便宜、无限容量、读不按行计费
D1 文章、分类关系、评论、用户、设置、文档索引 SQL 查询，列表页实时性的来源
KV 只存 site:ctx（站点设置快照） 读多写少，做跨 isolate 的配置缓存

这里有一条重要的工程约束：KV 的 list 操作很贵。早期版本把列表缓存、侧边栏、RSS 都放 KV，一次批量删除几百篇文章就会触发大量 list + delete，直接把免费额度打满。现在这些缓存全部搬到 Cache API（免费、不计 KV 配额），KV 只保留一个键。

为什么列表页不静态化

静态化列表页听起来更快，但会带来两个问题：

  • 每发一篇文章，首页、分类页、标签页、归档页、RSS 都要重新生成；
  • 分页是组合爆炸：分类 × 页码 × 标签，文章一多就生成不完。

而 D1 的列表查询是按行计费但读很便宜，加上边缘缓存，实际成本远低于维护一堆静态列表。所以这里的选择是：单页静态，列表动态。

三级降级生成

WordPress 侧生成单页时，按顺序尝试三种方式：

  1. 内部模板渲染：在 WP 进程内 load_template()，最快，样式最贴近主题；
  2. 前台抓取：模拟访问前台页面，把 HTML 抓下来；
  3. 硬编码兜底：前两种都失败时，用一份极简模板保证”至少有一页”。

这套降级是为了解决大批量导出时的 503：单篇失败不会让整批任务挂掉。

风格包为什么是”目录”

一套风格 = wp-content/themes// 下的 tpl.json + style.css + 资源文件。

tpl.json 里是 6 类页面的 HTML 骨架（首页、分类、标签、归档、单页、列表条目），用 {{POST_TITLE}} 这类占位符标记要填的值。渲染时只做字符串替换，不执行模板语言，所以：

  • 换风格 = 换一个目录，不需要重新部署 Worker；
  • 风格可以被抓取、被上传、被在线编辑；
  • 出问题可以直接切回上一个风格。

这套架构的边界

  • 单页是快照：换风格、改站点名、改 permalink 之后，旧单页不会自动变，需要重建；
  • 列表缓存按数据中心生效，跨地域最终一致；
  • 依赖 Cloudflare：D1 / R2 / KV / Workers 任意一个不可用，站点都会受影响。

接受这些边界，换来的是几乎为零的运维成本和足够好的访问速度。

5 分钟搭起一个 Cloudflare 独立 CMS

Posted on October 17, 2026 by admin

前置

  • Node.js ≥ 18
  • 一个 Cloudflare 账号（D1 / R2 / KV 都在免费额度内）
  • 本机可以运行 npx wrangler

1. 创建资源

cd worker
npx wrangler login

# 先看会创建什么（不产生任何资源）
node scripts/setup.mjs --dry-run

# 实际创建 D1 / KV / R2，并生成 wrangler.toml
node scripts/setup.mjs

脚本会在你的账号下创建三个资源，并把 ID 写进 wrangler.toml。已有资源的话，复制 wrangler.toml.example 手工填三个 ID 即可。

2. 部署

npm run deploy

这条命令会先扫描 static/wp-content/themes/ 生成内置风格索引，再执行 wrangler deploy。首次部署会要求你给 Worker 起一个名字、选一个 *.workers.dev 子域。

绑定自定义域名：Cloudflare Dashboard → Workers → 你的 Worker → Settings → Domains & Routes。

3. 初始化管理员

打开 https://<你的域名>/admin/。空库时会直接进入初始化向导，填：

  • 站点名
  • 站点 URL（例如 https://demo.example.com）
  • 管理员用户名与密码（至少 8 位）

提交后会创建第一个管理员并自动登录。

也可以用命令行：

curl -X POST https://<你的域名>/api/setup 
  -H 'Content-Type: application/json' 
  -d '{"username":"admin","password":"至少8位","siteName":"我的站","siteUrl":"https://<你的域名>"}'

⚠️ /api/setup 只在没有任何用户时可用。部署完请尽快初始化，避免被陌生人抢先建号。

4. 发布第一篇文章

后台 → 文章 → 新建：

  • 标题、slug（留空会按标题生成）
  • 编辑器切到 Markdown，写正文
  • 选分类（没有就先在分类页建一个）
  • 状态选 发布

保存后 Worker 会立即渲染单页写入 R2，并清理列表缓存。访问 https://<你的域名>// 就能看到。

5. 换一个风格

后台 → 模板 → 风格应用，下拉里会列出内置风格（14 套左右）。选一个，点应用。

列表页立即生效；已经生成的单页不会自动变，需要到「批量任务 → 重建全部单页」跑一遍。

常见卡点

  • /admin/ 打不开：确认 Worker 路由和自定义域已生效；首次部署后边缘生效需要几十秒。
  • 登录后一直跳回登录页：检查浏览器是否禁用了第三方 Cookie / 本地存储；JWT 存在 localStorage。
  • 文章 404：确认状态是 published，且 slug 没有和已有文章冲突。
  • 样式没变：单页是快照，换风格后要重建；列表页有几十秒缓存。

下一步

  • 后台导览：每个页面是干什么的
  • 风格系统：自己改一套皮肤
  • 从 WordPress 出发的路线

从 WordPress 出发：装插件、配目标、发第一篇文章

Posted on October 16, 2026 by admin

这条路线适合谁

  • 已经有 WordPress 站，文章、媒体、评论都在里面；
  • 不想迁移内容，也不想放弃 WP 的编辑器与插件；
  • 想让前台跑在 Cloudflare 上，最好还能省掉源站。

1. 安装插件

把 cf-static-export-pro 目录放进 wp-content/plugins/，在后台启用。

启用后左侧会出现「CF 静态导出」菜单。设置页分成两列：

  • 左列：托管目标、CMS 自托管设置（文章导出 / 评论同步 / Worker 端管理）
  • 右列：状态面板、静态托管设置、基础配置、最近日志

2. 配置一个 Cloudflare 目标

「🎯 托管目标 → 添加目标」，选 cloudflare，填：

字段 说明
账号 ID Cloudflare 账号 ID（Dashboard 右侧可见）
API Token 需要 D1 编辑 + R2 编辑权限
D1 数据库 ID Worker 绑定的那个 D1
R2 桶名 例如 wordpress
站点 URL 例如 https://demo.example.com
X-Auth-Key 与 Worker 的 AUTH_KEY 一致

填完点「测试连通性」，四项都通过再保存。

如果你只用 WordPress 导出、不用 Worker CMS，也可以把目标换成 S3、GitHub、Netlify、Vercel、FTP、WebDAV 或本地目录。

3. 选择发布行为

「发布行为」里三个开关决定一篇文章保存时做什么：

  • 同步 D1：把结构化数据写进 D1（列表页需要）；
  • 生成静态文件：在本地生成 HTML；
  • 上传远端：把 HTML 和媒体传到 R2。

第一次建议全开，先跑通链路。之后可以按需关闭，比如只同步 D1、不生成静态页。

4. 发布一篇文章

新建一篇普通文章，选分类，点发布。插件会在后台做三件事：

  1. 调 Worker 的 /d1-batch 写入文章与分类关系；
  2. 生成静态 HTML（内部模板 → 前台抓取 → 兜底）；
  3. 上传 R2，并清理列表缓存。

然后访问 https://<你的域名>// 验证。

5. 选一套列表页风格

Worker 渲染列表页需要模板。后台 → 模板 → 风格应用，内置风格可以直接选；想自己写的话，一套风格就是一个目录 + tpl.json + style.css，见风格系统。

换风格后列表页立即生效，已生成的单页需要重建。

6. 批量导出旧文章

文章列表页支持勾选 + 批量导出；也可以用 tools/bulk-export-worker.php 走 CLI，适合几千篇的站。

导出过程是分片 + 多进程并发的，单篇失败会记录日志但不阻塞整批。

和独立 CMS 的关系

两条路线不是二选一。常见做法是：

  • 继续用 WordPress 写长文；
  • 用 Worker CMS 管理分类、媒体与评论；
  • 需要时把 Worker 上的改动拉回 WordPress。

数据以 D1 为准，WordPress 侧只做”推送”，不会整行覆盖 CMS 的独有设置。

后台导览：内容、分类、媒体、模板、评论

Posted on October 15, 2026 by admin

后台地址是 /admin/。左侧导航按”内容 → 展示 → 运营 → 系统”排列。

文章

  • 列表支持搜索、按状态/分类/标签筛选、按日期或标题排序；
  • 表头有全选，底部可以批量发布、转草稿、删除；
  • 新建/编辑支持 Markdown 与 富文本 两个页签。当前格式对应的页签可编辑，另一个只读预览——这是为了避免切换页签把 Markdown 原稿污染成 HTML。

批量操作走的是”一次取数 + D1 批量提交 + R2 并发删除”，几十篇的批量通常几秒完成。

分类与标签

分类和标签共用一套 taxonomies 表，用 type 区分。可以新建、改名、改 slug、删除。

删除一个仍被文章使用的分类会被拒绝；要先把文章移到别的分类。

媒体库

  • 支持拖拽上传、网格/列表切换、按类型筛选、按时间排序；
  • 上传时会校验文件魔数，只接受常见图片格式；
  • 文件落在 R2 的 wp-content/uploads/YYYY/MM/，文件名统一小写并做 URL 编码。

模板 / 风格

两个部分：

  • 风格应用：从内置 + 用户风格里选一个，点应用；
  • 编辑模板：可视化编辑 6 类模板，或者直接改 JSON 源码。

改完保存只影响之后的渲染。已生成的单页需要重建才会套用新模板。

评论

  • 筛选：未回拉 / 待审核 / 全部；
  • 对 Worker 端收到的评论可以直接审核、删除；
  • 已由 WordPress 接管的评论只读，需要去 WP 后台改。

设置

  • 站点名、描述、URL、permalink 结构；
  • Logo、横幅、社交链接、导航菜单；
  • 缓存 TTL、列表每页文章数、批量任务并发；
  • head 自定义 HTML（统计脚本、meta 验证等）。

批量任务

长任务都放在这里：

  • 重建全部单页（可断点续做）；
  • 迁移 permalink（先复制、再切换、最后清理旧对象）；
  • 清理孤儿文件。

进度存在 D1，关掉页面再回来还能继续。

风格系统：一个目录就是一套皮肤

Posted on October 14, 2026 by admin

一套风格长什么样

wp-content/themes/my-style/
├── tpl.json      # 6 类页面的 HTML 骨架
├── style.css     # 样式
└── ...           # 图片、字体、JS

tpl.json 的结构：

{
  "name": "我的风格",
  "tpl": {
    "pageHome": "...",
    "pageCategory": "...",
    "pageTag": "...",
    "pageArchive": "...",
    "single": "...",
    "item": "..."
  },
  "sidebar": { "categories": "...", "archives": "...", "tags": "..." },
  "comments": { "list": "...", "entry": "...", "children": "...", "form": "..." }
}

item 是列表里单张卡片的骨架；sidebar 和 comments 是可选片段，缺省时用内置骨架。

占位符

模板里用 {{XXX}} 标记要填的值，用 {{#IF_XXX}}...{{/IF_XXX}} 做条件块。

常用的：

占位符 用在哪 含义
{{SITE_NAME}} / {{SITE_DESC}} / {{SITE_URL}} 全部 站点信息
{{MENU}} 全部 导航菜单
{{CONTENT}} 列表页 渲染好的文章卡片列表
{{TITLE}} 列表页 分类名 / 标签名 / 归档标题
{{POST_TITLE}} / {{POST_CONTENT}} / {{POST_DATE}} 单页 文章字段
{{POST_URL}} / {{POST_EXCERPT}} 条目 文章链接与摘要
{{PAGINATION_PREV}} / {{PAGINATION_NEXT}} 列表页 翻页
{{SIDEBAR_CATEGORIES}} 全部 分类列表片段

规则很简单：占位符必须和渲染器实现一致。写了未实现的占位符不会报错，但出口会被静默清空——所以改模板后最好在预览里检查一遍。

在线换肤

后台 → 模板 → 风格应用 → 选一个 → 应用。

背后只做了一件事：把 settings 表里 k='style' 的 active 改成风格 id。列表页下次请求就会用新模板渲染。

单页不会自动变。因为单页是 R2 里的静态快照，必须重建才会重新套模板。这也是为什么后台把「应用风格」和「重建全部单页」放在相邻的位置。

上传自己的风格

两种方式：

  1. 后台上传：模板 → 上传风格，选择一个目录（会递归读取文件），逐个写入 R2；
  2. 放进内置目录：把目录放到 worker/static/wp-content/themes//，npm run deploy。

内置风格会进 themes/index.json，所有部署都能看到；用户风格只存在 R2，换设备也在。

编辑模板

后台的可视化编辑器按 6 类页面分页签，支持：

  • 直接改 HTML；
  • 查看当前页面可用的占位符；
  • 保存后预览；
  • 切到 JSON 源码模式改整个文件。

保存前会把旧 tpl.json 备份为 tpl.json.bak，出问题可以回退。

静态站上的评论：提交、审核与回写

Posted on October 12, 2026 by admin

为什么静态站也能有评论

单页是静态 HTML，但评论区不必是静态的。

渲染单页时，模板里会留一段标记：

...

Worker 在返回 HTML 之前，按这个 id 查一次 D1 的 comments 表，把标记区间替换成最新评论。所以：

  • 页面主体仍然来自 R2，快；
  • 评论是请求时注入的，新评论、审核结果立即生效；
  • 不需要为了几条评论重建整页。

三条数据流

1. 读者在静态站提交

主题自带的评论表单会被改写成 action="/comments"，提交时走 fetch：

  • 蜜罐字段：机器人填了就静默丢弃；
  • 最小停留时间：少于 3 秒直接拒绝；
  • 内容校验：少于 2 个字、链接超过 2 个会被拒；
  • IP 限流：isolate 级滑窗。

写入 D1 时标记 origin='worker'、wp_comment_id=0、状态按站点设置（off / pending / auto）。

2. 在 Worker 后台审核

后台 → 评论，可以按”未回拉 / 待审核 / 全部”筛选。

对未回拉的评论可以直接通过或删除；已经由 WordPress 接管的评论是只读的。

3. 回写到 WordPress

如果站点同时跑 WordPress，可以开启定时回拉（默认每小时）：

  • 拉取 unpulled 的评论；
  • 在 WP 里创建评论（保留父子层级）；
  • 回写 D1 的 wp_comment_id 和 origin='wp'；
  • 下次不会再被拉一次。

WordPress 后台的评论也会通过钩子同步回 D1，保持两边一致。

开关

站点设置里的 comments 有三个字段：

字段 值 含义
mode off / embed / native 关闭 / 注入自定义片段 / 用内置评论系统
accept off / pending / auto 是否接受站外提交，以及是否需要审核
embed HTML mode=embed 时注入的第三方评论代码

已知限制

  • 没有验证码，强反垃圾需要接第三方；
  • 评论不分页，一次最多渲染 500 条；
  • 没有邮件通知（Worker 里发信需要额外服务）。

对个人站来说，蜜罐 + 停留时间 + 限流已经能挡掉绝大多数垃圾评论。

缓存与成本：为什么列表实时、单页飞快

Posted on October 11, 2026 by admin

三层缓存

层 缓存什么 失效方式
边缘 assets CSS / JS / 字体 / 主题图片 重新部署
Cache API 列表页、侧边栏、RSS TTL / 主动删除
KV 只存 site:ctx 改设置时重建

单页不进缓存层：它本身就是 R2 里的静态文件。

为什么把缓存搬出 KV

KV 的读写便宜，但 list 很贵。

早期版本用 KV 存列表页缓存，清理时要先 list 出所有键再逐个 delete。一次批量删除 500 篇文章，可能产生上千次 list + delete，免费额度很快就满了。

现在：

  • 列表缓存用 Cache API，键是内部 URL，没有列举能力，所以只删已知的固定键（home:page:1、sidebar:data、rss:feed 等），动态分页靠 TTL；
  • KV 只剩 site:ctx 一个键，站点设置快照，30 秒内存缓存 + 变更时主动清；
  • 批量任务进度、permalink 旧键清单从 KV 移到 D1。

结果是：发布/删除文章不再产生任何 KV 操作。

TTL 怎么设

后台 → 设置 → 缓存：

项 建议 说明
列表页 60–300 秒 越小越实时，越大越省 D1
侧边栏 300–3600 秒 分类/标签/归档变化不频繁
RSS 600–3600 秒 阅读器会自己轮询
站点信息 30–60 秒 改设置后最多等这么久

把某一项设为 0 表示关闭缓存、每次直查 D1。调试阶段可以这么做，稳定后建议开回来。

批量操作为什么变快了

旧实现是逐篇串行：查一次、写两次、删 R2 一次，100 篇就是几百次往返。

现在是：

  1. 一次 SELECT ... WHERE wp_id IN (...) 取出所有文章；
  2. 用 db.batch() 分块提交（D1 单次上限 100 条，按 50 切）；
  3. R2 操作用并发池（默认 8）；
  4. 渲染上下文（站点、侧边栏、模板）整批只取一次。

实测 10 篇删除约 3 秒，5 篇发布约 2.7 秒。

成本大概是多少

以免费额度为准：

  • Workers：10 万请求/天；
  • D1：5GB 存储，读按行计费；
  • R2：10GB 存储，读操作有免费额度；
  • KV：1GB 存储，10 万读/天。

一个日访问几百到几千的个人站，基本跑不出免费额度。真正容易超的是图片流量和高频动态列表，前者可以上 Cloudflare 缓存，后者调大 TTL。

一个容易忽略的点

单页是静态快照。以下操作之后，旧单页不会自动更新：

  • 换风格；
  • 改站点名 / 描述 / 菜单；
  • 改 permalink 结构；
  • 改模板。

需要到「批量任务 → 重建全部单页」跑一遍。列表页不受影响，它们每次请求都重新渲染。

在 Obsidian 里写完，一键发布

Posted on October 10, 2026 by admin

它做什么

obsidian-md-publisher 是一个零依赖的 Obsidian 插件。它把当前笔记的 Markdown 原文通过 WordPress REST 兼容端点发到站点：

  • 新建走 POST /wp-json/wp/v2/posts；
  • 更新走 PUT /wp-json/wp/v2/posts/；
  • 请求体带 content_format: "md"，站点按原稿存储，渲染时才转 HTML。

安装

  1. 把插件目录放进库的 .obsidian/plugins/obsidian-md-publisher/；
  2. Obsidian → 设置 → 第三方插件 → 关闭安全模式 → 启用；
  3. 如果改了 main.ts，重新构建：
npx esbuild main.ts --bundle --external:obsidian 
  --format=cjs --target=es2018 --outfile=main.js

配置

字段 说明
端点 URL https://<你的站点>/wp-json/wp/v2/posts
用户名 CMS 后台的用户名
应用密码 后台「用户 → 应用密码 → 生成」
自动上传图片 默认开，![[图.jpg]] 会先上传再替换
图片前缀 上传失败时的兜底路径

认证固定用 Basic（base64(用户名:应用密码)）。用 Bearer 会 401。

Frontmatter 约定

---
title: 文章标题
status: draft
slug: my-post
categories: [guide]
tags: [obsidian, markdown]
wp_id: 178974623300589
---
正文……
  • status 默认 draft，确认无误再改 publish；
  • categories / tags 建议写 slug；
  • 首次发布后插件会把返回的 id 写回 wp_id，之后同一个文件就是更新。

图片

开启自动上传后，笔记里的 ![[a.jpg]] 会：

  1. 读取本地附件；
  2. POST /wp-json/wp/v2/media 上传到 wp-content/uploads/YYYY/MM/；
  3. 把引用替换成返回的 URL。

支持 jpg / png / gif / webp，单图上限 10MB。SVG 不支持（避免 XSS）。

已知限制

  • 双链不会渲染：[[笔记]] 是 Obsidian 语法，Worker 用标准 CommonMark/GFM，不认。图片已经被插件转换，双链暂时保持原样；
  • 没有冲突检测：如果你在 CMS 后台改过同一篇，下一次从 Obsidian 发布会覆盖；
  • 没有重试队列：失败会在 Obsidian 里弹 Notice，正文不会丢。

为什么用 REST 而不是自定义 API

因为这套接口是 WordPress 生态的”通用语言”。除了 Obsidian，Ulysses、脚本、手机快捷指令、任何能发 HTTP 的工具都能接。

站点的写入口只实现了 WP REST 的一个子集：

  • GET/POST /wp/v2/posts
  • PUT/PATCH /wp/v2/posts/
  • GET /wp/v2/categories|tags
  • POST /wp/v2/media

够用，且不需要为每个编辑器写适配。

WordPress 插件：三级生成、多出口与版本升级

Posted on October 9, 2026 by admin

插件在链路里的位置

WordPress ──(插件)──> D1（结构化数据）
                    ├─> R2（静态单页 + 媒体）
                    └─> 其它托管（S3 / GitHub / Netlify / …）

插件负责三件事：生成、同步、发布。它不是 Worker 的一部分，而是”源站适配器”。

三级生成

单页 HTML 的生成按顺序降级：

一级：内部模板渲染

在 WP 进程内 load_template()，拿到主题渲染结果。最快、最贴近原主题。

有个坑：load_template() 是 require_once 语义，同一进程第二次渲染会得到空内容。插件用 get_included_files() 做了 guard。

二级：前台抓取

内部渲染失败时，模拟 HTTP 请求访问前台页面，把 HTML 抓下来。

CLI 环境下 home_url() 可能退化成 http://localhost，所以脚本支持 --site=<原站 URL> 在 wp-load 前补 $_SERVER。

三级：硬编码兜底

前两种都失败时，用一份极简模板保证”至少有一页”，并记录日志。

多出口

除了 Cloudflare，还支持：

  • S3 兼容存储
  • GitHub / GitLab
  • Netlify / Vercel
  • FTP / WebDAV
  • 本地目录

出口是”能力”的组合：有的支持上传，有的支持删除，有的支持 D1。插件按能力分派，不假设每个目标都一样。

版本 2.5.0 的主要变化

  • 列表每页文章数可配置；
  • taxonomies 升级复合主键 (type, slug)，修复同名分类/标签串数据；
  • 主题静态资源随 Worker 打包为 assets，边缘免费直出；
  • 清理死代码，新增 uninstall.php。

安装与升级

  1. 备份数据库；
  2. 停用旧版，覆盖插件目录；
  3. 启用后在设置页确认目标配置仍在；
  4. 如果表结构有变更，点一次「初始化 / 迁移」；
  5. 跑一遍「重建全部单页」。

插件不会自动改表结构，迁移需要手动触发，这是为了避免升级时静默改数据。
